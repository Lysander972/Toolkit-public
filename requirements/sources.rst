   .. code-block:: text

      1. 现有机制不应该连手动纠偏原始需求的能力都不给 原始需求本身并不长 所以可以通过看diff来确定是否有未经允许的篡改.
      2. 积压的archive应当具备合理的清除机制,避免永久性的膨胀. 比如允许集中地进行专门清除,并不受阻碍
      3. ID生成方式应尽可能地减少后续篡改的需求 比如UUID这种极难重复的东西就很不错
      4. 审计机制仍停留在简单表演层面,应该重新设计流程->
      旧版锚点审计 出于对CLI的局限性的考虑 参数单一; 但是相当于填了什么东西都能通过 那么为什么不显式要求一致性检查布尔值或者评分呢?
      部分模型自带合理化的对抗性的倾向,什么错误都可容忍的低标准 写死在权重里面的 提示词压不住. 因而离散评分大概比布尔值更好? 即使合理化了也应出于诚实不打满分 那么问题大概就找出来了?
      与此同时 门禁应该调整 分数足够阈值即可提交 但是应该有警告 给后续的专项审查留出入口
      
      现有的从需求到设计的锚定应同样这么做,在索要评论的同时要求打分
      以避免合理化导致布尔值失真的现象
      对于可追溯性的锚定 应该提供足够多的相关上下文 就像是锚点两侧的全文被截取出来一样 markdown里面把结构化文本提取应该不难吧?
      对解读的审计应该包括 需求的原文和解读评论
      key应该由文本内容生成 类似代码中的锚点
      
      对于从解读到决策这一层 同样地也是要求两侧原文覆盖
      评分 而非布尔值
      
      对于需求的解读也应更加完善 应该把推导的过程思路写下来 明确出发点和解读的角度等等 不能直接武断丢个解读结论
      而且需求原文应该对应着唯一且明确到底解读结论
      
      ## 此外需从根本上重新审视整个流程的设计
      
      从根本上审视当前的设计和需求的合理性 当前的OpenSpec流程的强制重新引入 是不是本身就不合理?
      我现在要的是完整的一套需求追踪 重点是保全原始需求 因为煤气灯太严重,几乎稳定的每次都能歪曲,进而导致设计上做出一些很弱智的东西 然后意图整个就歪掉 产物更是完蛋
      意图本身就被歪了
      现在重新梳理整个过程 发现新增的原始需求记录的解读决策过程 和OpenSpec的 Requirement块相重叠
      那么具体应该如何确定这些点的界限?
      
      OpenSpec本身这个载体是否合适 有没有更自然更完全统一的成熟选项
      如果一定要有OpenSpec 则OpenSpec这个流程应该怎么处理? 实际上强制要求changes并archive不管用 仍然可以纯走流程 纯添加了干扰性质的文档空转
      怎么让解读和决策的过程本身可以追溯? 是否有必要把 原始需求/解读/决策当中的部分或者全部直接写在OpenSpec文档而不再独立? 是否有必要让Requirement改为可选以链接代替正文等?
      
      
      核心在于对抗稳定的煤气灯和稻草人 即让"需求能够被正确地理解"以避免次次稳定地断章取义并以此为令牌合法化垃圾设计

      语言什么的不应该成为障碍(应该内部CLI统一充当中转层以消除这种内部碎片化)
